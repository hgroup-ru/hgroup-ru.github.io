# Как внести изменение

## Общий процесс

Для внешнего участника обычный путь такой:

1. сделать fork репозитория;
2. создать ветку;
3. внести изменение;
4. запустить локальные проверки, если окружение это позволяет;
5. открыть Pull Request;
6. исправить замечания CI/review в той же ветке.

Мейнтейнеры работают через короткие ветки в основном репозитории и тоже вливают изменения через Pull Request. Прямой обычный push в `main` не является рабочим процессом.

## Куда отправлять изменение

Сначала определите, к какому проекту относится правка:

- русский перевод, русская терминология, RU-specific UI/search, локальные Training Questions и явно локальные учебные диаграммы — меняются здесь, в `hgroup-ru/hgroup-ru.github.io`;
- оригинальный английский текст H-Group, игровая семантика source, official YML и официальные диаграммы — должны меняться в upstream [`hanabi/hanabi.github.io`](https://github.com/hanabi/hanabi.github.io).

Если вы нашли содержательную ошибку в upstream, которую видно и в русском переводе, предпочтительный путь — сначала предложить исправление upstream. H-Group RU не должен молча превращаться в независимую редакцию правил. Редкие осознанные исключения фиксируются отдельно в `localization/SOURCE_EXCEPTIONS.md`.

После принятия изменения upstream мейнтейнеры H-Group RU обновляют закреплённую revision и синхронизируют соответствующий русский материал.

## Кандидаты для upstream

Во время перевода и сопровождения RU-версии могут обнаруживаться исправления и улучшения, которые полезны не только русской локализации: ошибки оригинального текста, устаревшие UI-шаги, улучшения общих компонентов, новые диаграммы или другие изменения, которые разумно предложить официальному проекту.

Такие идеи публично собираются в [`localization/UPSTREAM_CANDIDATES.md`](localization/UPSTREAM_CANDIDATES.md). Любой участник может выбрать пункт, проверить его против текущего upstream и подготовить Pull Request в `hanabi/hanabi.github.io`. Само наличие пункта в списке не означает, что upstream обязан принять изменение; это очередь проверенных или требующих проверки кандидатов.

Если RU уже намеренно отличается от закреплённого source, активное отличие дополнительно фиксируется в `localization/SOURCE_EXCEPTIONS.md`. Эти два файла имеют разные задачи: `SOURCE_EXCEPTIONS.md` описывает текущее поведение RU, а `UPSTREAM_CANDIDATES.md` — что потенциально можно улучшить в оригинале.

## Локальная установка

Нужны Git, Node.js LTS и npm.

```bash
npm ci
npm run start
```

`npm run lint` также использует внешние CLI `yamllint` и ShellCheck. Если их нет, lint должен явно сообщить о недостающем инструменте; GitHub CI всё равно выполнит проверку в Linux-окружении.

## Проверки

Обычная проверка:

```bash
npm run lint
```

Если изменение затрагивает MDX/YML/rendering и вы хотите проверить production-сборку локально:

```bash
npm run build:ru
```

`npm run build` собирает все настроенные locale и не является обычной проверкой RU-изменений. Он нужен мейнтейнерам только для редких compatibility-проверок после upstream sync, крупных dependency/Docusaurus изменений или shared-code изменений.

Для PR из внешнего fork GitHub CI автоматически выполняет и lint, и `build:ru`, чтобы автор получил build-ошибки до merge.

## Источник смысла

Закреплённый официальный `hanabi/hanabi.github.io` — источник игрового смысла, структуры материала и official YML. Точная ревизия записана в `upstream.json`.

При содержательном изменении русской страницы:

- сверяйтесь с соответствующим официальным MDX/YML;
- сохраняйте все условия, исключения, примеры, предупреждения и силу формулировок (`must`/`should`/`can` и аналоги);
- не добавляйте новые игровые правила от себя;
- не «упрощайте» повторяющееся объяснение, если оно есть в source;
- учитывайте, что более поздний Level может намеренно уточнять раннее правило.

## Диаграммы

Official diagrams должны использовать YML из закреплённого upstream и штатный Hanabi Docusaurus renderer. Не реконструируйте официальную диаграмму вручную по тексту.

Проект также содержит семь явно локальных учебных YML-диаграмм. Они не являются official H-Group diagrams; их статус описан в `localization/README.md`.

## Training и Official Challenge Questions

Локальные Training Questions — материал H-Group RU, а не Official Challenge Questions. Не смешивайте эти категории в тексте или интерфейсе.

## Терминология

Следуйте `localization/TERMINOLOGY_RU.md`. Формальные Title Case названия H-Group conventions обычно остаются английскими.

Если source содержит известную ошибку или проект намеренно следует актуальному внешнему UI вместо закреплённого текста, сначала проверьте `localization/SOURCE_EXCEPTIONS.md`.

## Язык документации

Документация H-Group RU по умолчанию пишется на русском. Английский сохраняется там, где это технически важно: machine identifiers, команды, API/UI labels, формальные H-Group terms, неизменяемый upstream и лицензионный текст.

## Merge и публикация

Merge PR не публикует сайт автоматически. Релиз выполняется мейнтейнером отдельно через ручной GitHub Actions workflow `Release`.

## Лицензирование вкладов

Репозиторий распространяется на условиях, описанных в `LICENSE` и `LOCALIZATION_NOTICE_RU.md`. Отправляя Pull Request, участник подтверждает, что вправе предоставить свой вклад и разрешает распространять его на тех же условиях, которые применяются к соответствующему материалу репозитория (`CC BY-SA 4.0`, если для файла явно не указано иное).

Не добавляйте сторонний текст, изображения, данные или код, если у проекта нет права их распространять. Если материал имеет отдельную лицензию или требует атрибуции, явно укажите источник и условия в Pull Request.
