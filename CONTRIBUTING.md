# Как внести изменение

Спасибо, что хотите помочь H-Group RU. Для большинства правок процесс короткий: сделайте fork, создайте ветку, внесите изменение и откройте Pull Request.

## Куда отправлять правку

В этот репозиторий относятся:

- русский перевод;
- русская терминология;
- интерфейс, поиск и навигация русской версии;
- локальные Training Questions;
- явно обозначенные локальные учебные диаграммы;
- документация и tooling H-Group RU.

Правки оригинального английского текста H-Group, игровой семантики, официальных YML-файлов и официальных диаграмм лучше предлагать в [`hanabi/hanabi.github.io`](https://github.com/hanabi/hanabi.github.io).

Если проблема исходного проекта уже видна в русском переводе, не исправляйте игровую семантику молча. Осознанные локальные исключения перечислены в [`localization/SOURCE_EXCEPTIONS.md`](localization/SOURCE_EXCEPTIONS.md), а кандидаты на исправления upstream — в [`localization/UPSTREAM_CANDIDATES.md`](localization/UPSTREAM_CANDIDATES.md).

## Обычный процесс

1. Сделайте fork репозитория.
2. Создайте отдельную ветку.
3. Внесите изменение.
4. По возможности запустите подходящие локальные проверки.
5. Откройте Pull Request.
6. Исправляйте замечания CI и review в той же ветке.

Локальные проверки не являются условием для открытия PR: CI запустится автоматически. Если не уверены, достаточно открыть небольшой и понятный PR и описать, что именно вы меняете.

Автору Pull Request не нужно редактировать `CHANGELOG.md`, придумывать release note или добавлять служебный marker вроде `[no release note]`. Человекочитаемую историю релиза ведут мейнтейнеры: при подготовке Official Release они собирают заметные пользовательские изменения из принятых PR и приводят их к единому публичному тексту.

## Локальная установка

Нужны Git, Node.js LTS и npm.

```bash
npm ci
npm run start
```

## Проверки

Для большинства изменений достаточно:

```bash
npm run lint
```

Если правка затрагивает MDX, YML, компоненты, плагины, конфигурацию сайта или другой production-вход, дополнительно полезно проверить русскую сборку:

```bash
npm run build:ru
```

CI применяет то же правило автоматически и одинаково для внутренних PR и PR из fork: полный `build:ru` запускается, если diff затрагивает production-входы сайта. Канонический список таких входов хранится в `.github/workflows/publish.yml` (`on.push.paths`); отдельного списка специально для CI нет.

Если PR меняет только CI, release tooling или другую служебную документацию, которая не входит в production build, CI ограничивается быстрыми проверками и не собирает Docusaurus без необходимости.

### Форматирование PR

CI отдельно проверяет, меняет ли `npm run format` содержимое PR. Эта проверка выполняется с read-only permissions, без write-token и без repository secrets, поэтому одинаково безопасна для внутренних веток и fork PR.

Если форматирование ничего не меняет, дополнительного действия не требуется. Если нужны только механические formatter changes, workflow `PR Format Patch` приложит artifact `format-patch`. Его можно скачать из соответствующего GitHub Actions run и применить в своей ветке:

```bash
git apply format.patch
```

После этого закоммитьте результат и push-ните его в ту же ветку PR.

Для PR из ветки **этого же репозитория** мейнтейнер также может запустить команду `/format`: отдельный privileged workflow применит formatter и запушит механические изменения в PR-ветку. Для fork PR `/format` намеренно не получает возможность выполнять чужой код с write-token; используйте безопасный patch artifact.

Autofix не исправляет source-fidelity, терминологические решения, игровую семантику Hanabi или другие содержательные ошибки. Такие failures нужно разбирать по сообщению конкретной проверки или review.

## Если вы меняете перевод

Закреплённая версия [`hanabi/hanabi.github.io`](https://github.com/hanabi/hanabi.github.io) — источник игрового смысла, структуры официального материала и официальных YML-файлов. Точная revision записана в [`upstream.json`](upstream.json).

Подробные правила source-fidelity, progression, диаграмм и локальных дополнений собраны в [`localization/README.md`](localization/README.md). Принятая терминология — в [`localization/TERMINOLOGY_RU.md`](localization/TERMINOLOGY_RU.md).

Коротко:

- сохраняйте все существенные условия, исключения, примеры и объяснения;
- не меняйте степень обязательности формулировок;
- не добавляйте новые игровые правила от себя;
- официальные диаграммы берите из YML закреплённого upstream, а не восстанавливайте вручную по тексту;
- локальные Training Questions не являются Official Challenge Questions и не должны так называться.

## Язык документации

Документацию H-Group RU по умолчанию пишем на русском. Английские слова оставляем там, где это оправдано: команды, имена файлов и API, названия элементов интерфейса и формальные термины H-Group.

## Что написать в Pull Request

Достаточно трёх вещей:

- что изменено;
- зачем это нужно;
- какие проверки вы запускали, если запускали.

Если меняется содержание перевода, полезно указать соответствующую страницу или фрагмент upstream.

## Лицензирование вкладов

Условия распространения описаны в [`LICENSE`](LICENSE) и [`LOCALIZATION_NOTICE_RU.md`](LOCALIZATION_NOTICE_RU.md). Не добавляйте сторонний текст, изображения, данные или код, если у проекта нет права их распространять. Если материал имеет отдельную лицензию или требует атрибуции, укажите источник и условия в Pull Request.
