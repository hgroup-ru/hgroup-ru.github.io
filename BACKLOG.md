# Бэклог H-Group RU

Здесь находятся только открытые задачи и идеи, которые ещё требуют отдельного продуктового, редакционного или технического решения. Завершённая работа в этом файле не архивируется: история остаётся в Git и в [журнале изменений](CHANGELOG.md).

## Продукт

### Перевести и вынести Jeff's 2-player Score Hunting Guide

Отдельно локализовать важный companion resource — Jeff's Score Hunting Guide для игры вдвоём, на который сейчас есть лишь глубоко спрятанная ссылка в конце H-Group `misc/2-player.md`.

Источник на текущем сайте ведёт в репозиторий IAMJEFF (`iamwhoiamhahaha/hanabi`, `2-player/Score_Hunting_Guide.md`). Это внешний по отношению к основному H-Group source материал, поэтому до публикации перевода обязательно:

- зафиксировать точный source revision;
- проверить license/permission и требования к attribution;
- явно указать авторство IAMJEFF/Jeff и не представлять материал как официальный H-Group text, если источник сам этого не утверждает;
- перевести source-faithfully с отдельным semantic review сложных стратегических утверждений;
- сохранить оригинальную ссылку рядом с переводом.

После перевода сделать guide нормально discoverable: дать заметную ссылку рядом с основным 2-player guide и, при необходимости, отдельную карточку/related-resource block. Пользователь не должен находить этот важный материал только через `Optional Conventions → Score Hunting` в конце длинной страницы.

Selfish Conventions и Number Mute links, которые находятся рядом в том же source-блоке, не включать автоматически в scope этой задачи; оценить их отдельно при инвентаризации 2-player ресурсов.

### Чем игра вдвоём отличается от игры втроём и более

Добавить на страницу [«Игра вдвоём»](i18n/ru/docusaurus-plugin-content-docs/current/two-player.mdx) короткий авторский блок о том, **зачем вообще выбирать Hanabi на двоих** и какие компромиссы у этого формата по сравнению с партией на 3+ игроков.

Это должен быть содержательный companion к самим 2-player conventions, а не рекламный текст и не длинное эссе. Jeff в Score Hunting Guide кратко затрагивает похожую тему; использовать этот фрагмент как один из источников/поводов для проверки идей, но не ограничиваться им и не копировать его формулировки. Новый блок должен быть самостоятельным редакционным текстом H-Group RU.

Перед написанием отдельно разобрать, какие различия действительно следуют из структуры игры на двух игроков, а какие являются следствием конкретных H-Group 2-player conventions. В финальном тексте не смешивать эти категории.

Полезно коротко раскрыть обе стороны:

- чем формат на двоих может быть привлекательнее: другой ритм принятия решений, более тесная взаимозависимость двух рук, иная цена каждой подсказки/ошибки, возможность глубже читать одного партнёра и другие реально подтверждаемые особенности;
- чем он может быть беднее или сложнее 3+ player Hanabi: меньше разнообразия взаимодействий между несколькими перспективами, другой набор доступных линий и conventions, более высокая чувствительность к отдельным решениям и другие подтверждаемые trade-offs;
- кому такой формат может особенно понравиться и почему, без попытки объявить 2-player объективно «лучше» или «хуже»;
- как эти особенности связаны с тем, почему для игры вдвоём у H-Group существует отдельный supplemental framework.

Можно позволить себе умеренную редакционную интерпретацию и небольшую «спекуляцию», если она помогает объяснить ощущение формата, но такие места должны оставаться конкретными и проверяемыми по игровой логике. Не раздувать раздел в нейрослоп, философское эссе или универсальные утверждения о психологии игроков. Ориентир — несколько плотных абзацев или компактные «Плюсы / Компромиссы», которые дают читателю полезную модель формата за пару минут.

Перед публикацией сверить материал с Jeff's guide, официальным H-Group 2-player source и реальной механикой/конвенциями страницы, затем отдельно пройти semantic review спорных сравнительных утверждений.

### Контекстный возврат

Проверить необходимость отдельного Contextual Back только после реального использования обычной browser history, canonical links и сохранения состояния поиска в URL.

Не восстанавливать старую floating-кнопку только ради соответствия retired RU runtime.

### Интерактивные многошаговые примеры

Исследовать возможность превратить часть статических Hanabi-примеров в последовательность состояний, которую можно проматывать по ходам.

Желаемый UX:

- кнопки предыдущего/следующего шага;
- короткая подпись к каждому ходу;
- подсветка карт, которые важны на текущем шаге;
- возможность показать, например, выдачу Finesse, выделить все карты connection, а затем пошагово показать их розыгрыш;
- при необходимости — стрелки или другие лёгкие annotations поверх состояния.

Первый milestone — один proof-of-concept на хорошем многошаговом Finesse-примере.

Реализация должна расширять существующую модель Hanabi diagrams/states, а не создавать отдельный game engine или второй SPA-runtime. Без JS исходный MDX и статическая версия примера должны оставаться читаемыми.

### Просмотр диаграмм

Возвращаться к отдельному полноэкранному diagram modal только если текущих zoom/pan-возможностей Mermaid и штатных H-Group diagrams реально недостаточно.

При реализации обязательны корректные close, Escape, backdrop и focus/accessibility semantics.

### Широкие таблицы

Добавлять отдельные стрелки или другие controls для широких таблиц только после подтверждённой проблемы текущего horizontal-overflow UX Docusaurus.

## Редакционный и semantic QA

### Локальные challenge-style вопросы для будущих Levels

Исследовать создание авторских учебных задач, по глубине и структуре похожих на Official Challenge Questions, но всегда явно обозначенных как локальные Training/Challenge-style Questions и никогда не выдаваемых за официальный материал H-Group.

Это high-quality editorial/research task: важнее качество и однозначность каждой позиции, чем количество вопросов. При составлении задачи для конкретного Level нужно учитывать не только материал этого Level, но и **все конвенции, разрешения, приоритеты и исключения предыдущих Levels**, которые игрок к этому моменту уже обязан знать. Нельзя строить позицию в вакууме или проверять правило так, будто более ранних конвенций не существует.

Первый пилот сделать **только для Level 10**. До генерации вопросов отдельно перечитать и построить рабочую карту применимых конвенций Levels 1–10 и возможных взаимодействий между ними. Затем подготовить небольшой, но сильный набор позиций разных типов, например:

- «перечислите все эффективные/разумные ходы»;
- «найдите самый эффективный ход и объясните, почему он лучше альтернатив»;
- «сработает ли такой-то ход / такая-то интерпретация в этой позиции?»;
- «что должен заключить игрок после конкретной последовательности действий?»;
- «какие линии разрешены, какие запрещены и каким правилом?»;
- позиции с несколькими правдоподобными кандидатами, где нужно применить приоритеты конвенций, а не узнать термин по формулировке вопроса.

Для каждой позиции обязательны:

- конкретное состояние стола, рук, подсказок, discard и relevant history, достаточное для однозначного решения;
- проверка, что состояние физически и логически возможно;
- полный разбор всех существенно правдоподобных ходов, а не только объявление правильного ответа;
- проверка результата против всех правил Levels 1–10, включая более ранние conventions, которые могут изменить ответ;
- отсутствие скрытой информации, которую условие не предоставляет игроку;
- отсутствие вопроса, который сам термином или формулировкой выдаёт проверяемый механизм;
- естественное разнообразие позиций и форматов, а не серия косметических вариаций одного и того же шаблона;
- явное разделение между «единственно правильным», «лучшим по эффективности» и «допустимым, но менее эффективным» ходом;
- semantic QA на неоднозначность, ложные альтернативы и случайные нарушения conventions до показа пользователю.

После подготовки пилота Level 10 **не публиковать и не масштабировать автоматически**. Сначала показать весь набор пользователю на содержательную вычитку и дождаться явного одобрения качества, сложности и стиля. Только если пилот окажется удачным, отдельно решить, стоит ли раскатывать методику на последующие Levels и в каком объёме.

### Самостоятельные правила Hanabi и вход в H-Group

Создать на RU-сайте самостоятельную страницу с базовыми правилами Hanabi, написанную с нуля как понятный onboarding перед Руководством для начинающих. Это **не перевод и не адаптация официального буклета**: описывать игровую механику своими формулировками, со своей структурой, примерами и редакционным голосом.

Страница должна быть одновременно точной и живой. Можно использовать собственные шутки, литературные вставки и лёгкие пиротехнические метафоры, если они не размывают границу между правилом и художественным текстом и не мешают однозначно понять механику.

Обязательный scope:

- объяснить цель игры, устройство колоды/руки, жетоны подсказок и ошибок, три действия на ходу, допустимую подсказку, розыгрыш, сброс, добор, завершение колоды и подсчёт результата;
- ясно отделить **официальную игровую механику** от H-Group conventions: правила определяют, что игроку разрешено сделать, а conventions помогают группе договориться, что конкретное действие обычно означает;
- добавить короткий блок «Зачем вообще нужны конвенции?» без преждевременного обучения конкретным продвинутым conventions; после локализации подходящих `misc`-эссе можно дать оттуда необязательные ссылки на более глубокое чтение о целях, накоплении и стилях conventions;
- завершить страницу практическим советом: если после чтения механика всё ещё ощущается абстрактно, сходить на Hanab Live и сыграть одну-две обычные пробные партии, а затем вернуться к Руководству для начинающих;
- сделать естественный reading flow **Правила → попробовать пару партий → зачем нужны conventions → Руководство для начинающих**;
- заменить в Beginner текущую внешнюю ссылку на upstream `misc/rules.md` локальной ссылкой на эту страницу и сохранить совет новичку сначала сыграть одну-две партии;
- явно отметить на странице, что это самостоятельное изложение правил H-Group RU, а не официальный перевод rulebook.

Визуальная часть также должна быть оригинальной. Подготовить собственные иллюстрации/диаграммы там, где они реально ускоряют понимание: например, пример руки, корректной подсказки, игровых стопок, сброса и финального круга. Не копировать официальный artwork, дизайн карточек, сканы страниц или характерное художественное оформление издателя. Иллюстрации должны быть понятны без цвета как единственного носителя смысла и иметь разумные accessibility semantics.

Copyright/legal boundary сохранить консервативной: не переносить характерные формулировки, литературное вступление, шутки, таблицу художественных оценок или другую узнаваемую expression из официального буклета. Если для точности понадобится сверяться с официальными правилами, использовать их только как источник фактов о механике и написать итоговый текст независимо.

Перед публикацией отдельно проверить factual correctness правил, внутреннюю непротиворечивость примеров, мобильную читаемость иллюстраций, local links и полный `build:ru`. Эта задача является отдельным авторским/editorial PR и не должна раздувать source-faithful batch переводов `misc`.

### Обзор других систем конвенций Hanabi

Сделать отдельную обзорную страницу о других заметных системах и наборах конвенций Hanabi, чтобы читатель понимал, что H-Group — один из возможных подходов к командной коммуникации, а не единственный способ играть.

Страница должна быть навигационной и сравнительной, а не ещё одним учебником. Для каждой включённой системы или школы:

- дать короткое нейтральное описание: общая идея, характерный стиль игры, насколько система формализована и чем примерно отличается от H-Group;
- указать, для какой аудитории или контекста этот подход обычно полезен: casual group, BGA, expert play, alternative framework и т. п.;
- дать canonical link на первоисточник или лучший поддерживаемый обзор;
- явно указывать авторство/сообщество и не представлять сторонние conventions как часть H-Group;
- не копировать большие фрагменты чужой документации и не пересказывать систему настолько подробно, чтобы обзор превращался в неавторизованный substitute source;
- если для конкретной системы существует хороший русский материал, давать ссылку на него; если нет — честно отмечать язык внешнего источника.

Перед составлением страницы провести отдельную небольшую research-инвентаризацию и определить устойчивый список действительно заметных систем/подходов. Не включать случайные домашние conventions только ради количества. В initial candidate pool проверить как минимум BGA-style conventions, Hat-Guessing/Empty-Clues-подобные frameworks и другие хорошо задокументированные community systems, которые реально встречаются вне H-Group.

Важно разделять **систему конвенций**, **отдельную convention** и **вариант правил игры**: страница не должна превращаться в каталог всех известных Hanabi-трюков. Если между системами есть спорные оценки эффективности или сложности, описывать различия нейтрально и по возможности опираться на собственные источники систем, а не ранжировать их от имени H-Group RU.

По месту на сайте это должен быть discoverable companion к материалам «Зачем нужны конвенции?», `convention-styles` и странице «О проекте». При появлении собственной страницы базовых правил можно также дать оттуда ненавязчивую ссылку для читателя, которому интересно, какие ещё существуют способы договориться о смысле подсказок.

### Аудит внешних англоязычных материалов и ссылок

Автоматически проинвентаризировать пользовательские ссылки по всему RU-сайту, которые ведут на внешние текстовые материалы и могут оставлять читателя на английской странице: GitHub `blob`/`raw`, Markdown/MDX-файлы, внешние guides, appendices, examples и аналогичные документы.

Каждую такую ссылку классифицировать:

- официальный H-Group upstream material;
- сторонний авторский ресурс;
- source/attribution link, который должен оставаться внешним;
- техническая или служебная ссылка, не являющаяся частью пользовательского reading flow.

Для пользовательских англоязычных материалов, которые реально нужны русской версии:

- если это официальный материал из нашего pinned upstream, локализовать его source-faithfully и опубликовать на нормальном RU destination;
- если это сторонний ресурс, сначала зафиксировать точную revision/version и проверить license/permission и attribution; переносить перевод к нам только когда это разрешено;
- сохранить авторство и оригинальную source-ссылку рядом с локальной версией, когда это важно для provenance;
- после появления локальной версии заменить пользовательские переходы на canonical RU-link, не удаляя необходимый source/attribution access;
- если републикация невозможна по лицензии или разрешению, не копировать текст молча: отдельно решить допустимый RU-сопроводительный вариант и сохранить внешний источник;
- прогнать link QA, чтобы не осталось маршрутов, где русская статья неожиданно отправляет пользователя читать английский файл только потому, что так было устроено в upstream.

Этот аудит должен включать не только основной H-Group repository: внешние репозитории и авторские guides тоже входят в scope.

### QA coverage registry

Продумать лёгкий способ фиксировать, какие материалы уже прошли отдельные виды review: source-fidelity, Training Questions, diagram review и whole-site consistency.

Цель — при будущих обновлениях перепроверять в первую очередь новые и изменившиеся материалы, а не запускать полный ручной аудит всего сайта с нуля.

Не превращать registry в тяжёлую ручную базу данных или формальную бюрократию.

### Единый audit pipeline

По возможности свести повторяемые проверки в один воспроизводимый pipeline/report: upstream drift, структура, терминология, подозрительные translation pairs, Training Questions, ссылки, labels/consistency и diagram coverage.

Итог должен быть ориентирован на проблемы и предлагаемые исправления, чтобы человеку не приходилось вручную просматривать успешные проверки.

## Contributor experience

### CI autofix для внешних контрибьюторов

Добавить безопасный механизм автоматического исправления технических ошибок в PR от внешних контрибьюторов там, где исправление детерминировано и не меняет смысл материала.

В первую очередь рассмотреть:

- Prettier и другие formatter-only исправления;
- простые ESLint fixes, для которых `--fix` не меняет семантику;
- нормализацию trailing newline / whitespace и аналогичные механические проблемы;
- при необходимости — понятный комментарий CI о том, что было исправлено автоматически, а что осталось ручным.

Отдельно проверить модель GitHub permissions для fork PR. Нельзя небезопасно выполнять непроверенный код из внешнего PR с write-token или secrets. Если прямой push в ветку автора невозможен или небезопасен, выбрать безопасную архитектуру: например, разделить untrusted validation и privileged autofix, использовать maintainer-triggered workflow либо выдавать готовый patch/commit suggestion.

Autofix не должен пытаться самостоятельно исправлять source-fidelity, терминологические решения, смысл Hanabi-конвенций или другие semantic failures. Такие проверки должны оставаться diagnostic-only и объяснять контрибьютору, что именно нужно решить.

### Ревизия публичной документации для контрибьюторов

Вычитать Markdown-документы публичного репозитория как contributor-facing продукт и определить, какие из них действительно нужны внешнему участнику, насколько понятно они написаны и нет ли там исторического или внутреннего maintainer-контекста, который только мешает.

Начальный scope включает как минимум `README.md`, `CONTRIBUTING.md`, `ARCHITECTURE.md`, `LOCALIZATION_NOTICE_RU.md`, `Reference.md` и другие корневые/служебные `.md`, которые видит потенциальный контрибьютор. Для каждого файла классифицировать назначение: onboarding, contribution workflow, архитектура, provenance/legal, compatibility redirect, maintainer-only или кандидат на удаление/слияние.

Проверить:

- понятно ли человеку без внутреннего контекста, что это за проект и куда отправлять разные типы правок;
- достаточно ли короток путь от README до первого успешного PR;
- не дублируют ли README/CONTRIBUTING/ARCHITECTURE друг друга;
- актуальны ли команды, CI expectations, naming/branch conventions и описание структуры репозитория;
- хорошо ли объяснена граница между upstream H-Group content и локальными RU-дополнениями;
- нет ли инструкций, которые нужны только maintainers и должны жить в приватном maintainer repo;
- можно ли что-то сократить, объединить или удалить без потери полезного contributor guidance;
- нужны ли дополнительные короткие разделы вроде «быстрый старт», «что можно править», «как проверить изменение» и «что произойдёт после открытия PR».

Результатом должен быть конкретный proposal по каждому contributor-facing `.md`: оставить, переписать, сократить, дополнить, объединить, перенести или удалить. После согласования сделать один компактный docs cleanup batch, а не серию косметических PR.

## Локальные учебные диаграммы

### Расширить coverage в Extras и Variant-Specific

Автоматически пройти Extras и подходящие Variant-Specific материалы, найти длинные или многошаговые примеры без достаточной визуализации и составить ranked candidate list.

Для сильных кандидатов подготовить локальные teaching YML/diagrams, прогнать schema/render/semantic QA и затем показать человеку готовую галерею для содержательной приёмки.

Не добавлять авторские схемы только ради количества: каждая должна объяснять реальную сложную структуру примера лучше текста.

Текущие известные кандидаты:

- [`extras/ejections`](i18n/ru/docusaurus-plugin-content-docs/current/extras/ejections.mdx) — Trash Push Ejection / Bad Chop Move Ejection;
- [`extras/special-bluffs`](i18n/ru/docusaurus-plugin-content-docs/current/extras/special-bluffs.mdx) — Pass / Double Pass / Triple Pass Bluff;
- [`extras/pushes-pulls`](i18n/ru/docusaurus-plugin-content-docs/current/extras/pushes-pulls.mdx) — Trash Pull и взаимодействие с Trash Double Ignition;

## Сопровождение upstream

### Upstream drift check перед крупными продуктовым изменениями

Перед следующим большим product batch сравнить закреплённую revision из [`upstream.json`](upstream.json) с текущим official upstream и понять, появились ли изменения MDX/YML/структуры, которые разумнее забрать до новой реализации.

Не обновлять pin автоматически только ради свежести. Если drift не затрагивает наш scope или не даёт полезных изменений, оставить текущую revision.

## Кандидаты для исходного проекта

Ошибки и улучшения, которые потенциально относятся не только к русской версии, ведутся отдельно в [`localization/UPSTREAM_CANDIDATES.md`](localization/UPSTREAM_CANDIDATES.md). Не дублировать их здесь.
