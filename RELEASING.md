# Публикация и релизы H-Group RU

Эта инструкция описывает три разных жизненных цикла: проверку Pull Request, публикацию текущего сайта и официальный релиз. Их нельзя смешивать.

## Коротко

- **CI** проверяет PR и не меняет production.
- **Publish Site** собирает текущий `main` и публикует GitHub Pages. Он не создаёт tag, GitHub Release и не потребляет release notes.
- **Official Release** публикует тот же source через тот же Publish workflow, после чего создаёт `prod-*` tag, GitHub Release, архивирует `## Следующий релиз` и синхронизирует maintainer state.

`Publish Site` — это способ доставить изменения пользователям. `Official Release` — человекочитаемый checkpoint и публичный отчёт о накопившемся пакете изменений.

## Человекочитаемая история

Пользовательские заметки накапливаются в секции `## Следующий релиз` файла [`CHANGELOG.md`](CHANGELOG.md) **независимо от того, опубликованы изменения на сайте уже или ещё нет**.

Релизные заметки пишутся для людей, а не как журнал коммитов. Хорошая заметка сначала отвечает на вопрос «что стало лучше или что теперь можно сделать», а уже потом при необходимости уточняет деталь.

Обычно в заметки входят:

- новые страницы, переводы и пользовательские возможности;
- заметные улучшения навигации, поиска и интерфейса;
- исправления, которые меняют поведение сайта или содержание материала;
- важные уточнения правил и контекста, которые увидит читатель.

Обычно не входят:

- cleanup `BACKLOG.md`;
- branch cleanup и настройки репозитория;
- перестройка CI и release machinery без пользовательского эффекта;
- технические refactor-правки;
- проверки, которые сами по себе ничего не меняют для читателя.

Если user-facing изменение уже опубликовано через `Publish Site`, оно **остаётся** в `## Следующий релиз` до следующего Official Release.

## Формат `Следующий релиз`

Если изменения есть, секция содержит один непустой `release-title`:

```md
## Следующий релиз

<!-- release-title: Короткий человекочитаемый заголовок -->

Короткое вводное предложение о сути пакета.

### Добавлено

- Что нового появилось для читателя.

### Улучшено

- Что стало понятнее, удобнее или быстрее.
```

Комментарий `release-title` не попадает в GitHub Release. Он используется при автоматическом архивировании для заголовка вида `## YYYY-MM-DD — ...`.

Если пользовательских изменений после последнего Official Release нет, используется точный placeholder:

```md
_Изменений для следующего релиза пока нет._
```

В пустой секции `release-title` не нужен.

## CI

Обычный PR CI остаётся быстрым: invariant checks, формат/типизация/линт и другие проверки из `npm run lint`. Полный RU build не обязателен для каждого внутреннего PR.

Fork PR дополнительно собирается полностью, потому что для внешнего контрибьютора полезно получить build failure до merge.

CI не публикует сайт и не создаёт release metadata.

## Publish Site

Canonical workflow: `.github/workflows/publish.yml`.

Он единственный содержит реализацию GitHub Pages deployment:

1. checkout source;
2. setup;
3. `npm run build:ru`;
4. upload Pages artifact;
5. `actions/deploy-pages`.

Publish запускается:

- автоматически после `push` в `main`, если изменились входы сайта (`docs`, `i18n`, `src`, `static`, Docusaurus/sidebar/package/build setup);
- вручную через Actions → `Publish Site`;
- машинно закрытием служебного issue `Publish Site Control` (#102);
- как reusable workflow из Official Release.

Publish **не** создаёт `prod-*` tag, GitHub Release и не архивирует `CHANGELOG.md`.

Изменения только в CI, release machinery, backlog и другой служебной документации не должны бессмысленно пересобирать сайт, если они не являются входами его production build.

## Official Release

Canonical workflow: `.github/workflows/release.yml`.

Перед запуском убедитесь, что:

1. `main` содержит задуманный пакет;
2. `## Следующий релиз` описывает все заметные user-facing изменения после прошлого Official Release, включая уже опубликованные через Publish;
3. есть корректный `release-title`;
4. текст читается как публичный отчёт, а не список PR;
5. PR CI зелёный.

Official Release можно запустить вручную через Actions → `Release` или закрытием служебного issue `Release Control` (#100).

Workflow:

1. проверяет свежесть и формат release notes;
2. вызывает canonical `Publish Site` и публикует тот же source SHA;
3. создаёт `prod-YYYYMMDD-N` tag;
4. создаёт GitHub Release с человекочитаемым текстом из `## Следующий релиз`;
5. архивирует выпущенную секцию в историю `CHANGELOG.md` с отдельной технической трассировкой;
6. синхронизирует objective official-release facts в maintainer state.

После архивации `## Следующий релиз` снова становится пустым.

## Что является source of truth

- текущий live deployment и его SHA: GitHub Pages deployment history;
- накопленные пользовательские изменения после прошлого official release: `CHANGELOG.md` → `## Следующий релиз`;
- история официальных выпусков: архив `CHANGELOG.md` + GitHub Releases + `prod-*` tags;
- будущие задачи: `BACKLOG.md`;
- private maintainer state хранит release/maintainer facts, но не подменяет GitHub Pages как источник истины о текущем live deployment.

## Если что-то упало

Если обычный Publish упал, новый source не считается опубликованным. Исправьте причину и повторите Publish для актуального `main`.

Если Official Release упал **до** успешного Publish, исправьте причину и запускайте релиз заново с актуального `main`.

Если Publish внутри Official Release уже прошёл, а упал последующий metadata/archive/state этап, не запускайте новый deploy вслепую. Сначала определите упавший этап; если source SHA не меняется, допустим rerun соответствующего failed job/attempt.

Если для исправления требуется новый commit в `main`, старый run остаётся привязан к старому SHA. Сначала опубликуйте актуальный `main`, затем запускайте новый Official Release, когда `## Следующий релиз` корректно описывает пакет.

Не заявляйте browser QA, production-поведение или иные проверки, если они фактически не выполнялись.
