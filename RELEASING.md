# Релизы H-Group RU

Эта инструкция предназначена для мейнтейнеров H-Group RU. Пользовательские заметки к релизу готовятся в секции `## Следующий релиз` файла [`CHANGELOG.md`](CHANGELOG.md); Production Release использует эту секцию как источник текста GitHub Release, а после успешной публикации архивирует её в историю.

## Главный принцип

Релизные заметки пишутся для людей, а не как журнал коммитов.

Хорошая заметка сначала отвечает на вопрос «что стало лучше или что теперь можно сделать», а уже потом при необходимости уточняет деталь. Не перечисляйте имена файлов, номера Pull Request, внутренние refactor-задачи и устройство CI, если это не имеет самостоятельного пользовательского эффекта.

Обычно в релиз стоит включать:

- новые страницы, переводы и пользовательские возможности;
- заметные улучшения навигации, поиска и интерфейса;
- исправления, которые меняют поведение сайта или содержание материала;
- важные уточнения правил и контекста, которые увидит читатель.

Обычно не стоит включать:

- cleanup `BACKLOG.md`;
- branch cleanup и настройки репозитория;
- перестройку CI и release machinery без пользовательского эффекта;
- технические refactor-правки;
- проверки, которые сами по себе ничего не меняют для читателя.

## Обязательный формат `Следующий релиз`

Если для следующего релиза уже есть изменения, секция должна содержать непустой `release-title`:

```md
## Следующий релиз

<!-- release-title: Короткий человекочитаемый заголовок -->

Короткое вводное предложение о сути релиза.

### Добавлено

- Что нового появилось для читателя.

### Улучшено

- Что стало понятнее, удобнее или быстрее.
```

`release-title` должен находиться на отдельной строке и иметь вид:

```md
<!-- release-title: ... -->
```

Этот комментарий не попадает в текст GitHub Release. Он нужен release pipeline для исторического заголовка вида `## YYYY-MM-DD — ...` при автоматическом архивировании заметок.

Если изменений для следующего релиза пока нет, используется точный placeholder:

```md
_Изменений для следующего релиза пока нет._
```

В пустой секции `release-title` не нужен.

## Как писать хороший текст

- Используйте короткий заголовок релиза, который описывает тему пакета, а не внутреннюю задачу.
- Для небольшого релиза полезно начать с одной вводной фразы, объединяющей изменения в понятную историю.
- Группируйте пункты по смыслу. Обычно достаточно `Добавлено`, `Улучшено`, `Изменено` и `Исправлено`; пустые разделы не создавайте.
- Формулируйте пункты через пользовательский результат: «опубликован русский перевод», «ссылка теперь ведёт на русскую страницу», «поиск стал…».
- Не превращайте release notes в технический отчёт. Детали CI, SHA, PR и внутренних файлов остаются в Pull Request и автоматической трассировке архива.
- Сохраняйте принятую терминологию H-Group и естественный русский язык. Формальные названия conventions оставляйте там, где это важно для смысла.
- Не заявляйте проверки, browser QA или production-поведение, если они фактически не выполнялись.
- Если уже опубликованный GitHub Release вручную отредактировали после автоматического архивирования, синхронизируйте соответствующий исторический блок в `CHANGELOG.md`, чтобы публичный Release и журнал изменений не расходились по смыслу.

## Перед Production Release

Перед запуском workflow проверьте:

1. `main` содержит весь задуманный релизный пакет.
2. В `CHANGELOG.md` заполнен `## Следующий релиз`.
3. Если секция не пустая, в ней есть корректный `release-title`.
4. Текст читается как публичная заметка для пользователя, а не как список PR.
5. Обычный PR CI зелёный.
6. Production Release запускается вручную с актуального `main`.

Release workflow дополнительно проверяет свежесть заметок, выполняет lint и полный RU build, публикует GitHub Pages, создаёт production tag и GitHub Release, запускает Algolia crawler и затем архивирует выпущенную секцию `Следующий релиз`.

## Если release workflow упал

Сначала определите, на каком этапе произошёл сбой.

- Если исправление не требует менять released source SHA, например проблема во внешней конфигурации post-release шага, допустим rerun соответствующего failed job или attempt.
- Если для исправления нужно внести новый коммит в `main`, старый workflow run не подходит: rerun останется привязан к исходному SHA. После merge исправления запускайте новый Production Release с актуального `main`.

Не считайте merge в `main` публикацией: Production Release остаётся отдельным ручным gate.
